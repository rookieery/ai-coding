# PRD 生成器

为当前五子棋/中国象棋全栈项目生成结构化的产品需求文档。

---

## 核心职责

1. 接收用户的功能描述
2. 提出 3-5 个关键澄清问题（带字母选项）
3. 基于回答生成结构化 PRD
4. 保存到 `tasks/prd-[feature-name].md`

**重要：** 不要开始实现代码，只创建 PRD 文档。

---

## 第一步：澄清问题

仅在初始需求模糊时提问，聚焦于：

- **问题/目标：** 解决什么问题？
- **核心功能：** 关键动作是什么？
- **范围/边界：** 不应该做什么？
- **成功标准：** 怎么算完成？

### 问题格式（字母选项 + 可缩写回答）

```
1. 这个功能的主要目标是什么？
   A. 改善用户体验
   B. 增加留存率
   C. 减少客服负担
   D. 其他: [请说明]

2. 目标用户是谁？
   A. 仅新用户
   B. 仅老用户
   C. 所有用户
   D. 仅管理员
```

用户可回答 `1A, 2C` 快速迭代。

---

## 第二步：PRD 结构

生成的 PRD 必须包含以下段落：

### 1. 概览
功能简述及解决的问题。

### 2. 目标
具体、可衡量的目标（bullet list）。

### 3. 用户故事
每个用户故事需要：
- **标题：** 简短描述性名称
- **描述：** "作为 [角色], 我想要 [功能], 以便 [价值]"
- **验收标准：** 可验证的完成条件清单

每个 Story 必须足够小，能在**一次 Ralph 迭代（一个 context window）**内完成。

**格式：**
```markdown
### [PREFIX-XXX]: [标题]
**描述:** 作为 [角色], 我想要 [功能], 以便 [价值]

**验收标准:**
- [ ] 具体的可验证标准（明确输入/输出/行为）
- [ ] TypeScript 编译通过
- [ ] 相关单元测试通过
- [ ] （如有 UI 变更）使用 Chrome DevTools MCP 验证渲染
```

**重要规则：**
- 验收标准必须可验证，禁止模糊表述。"工作正常"是坏的。"按钮点击后弹出确认对话框"是好的。
- **Story ID 前缀**：使用项目约定的前缀（如 `ONLINE-`、`XIANGQI-`），从当前最大编号 +1 开始。需读取 `prd_archive.json` 和 `prd.json` 获取已有编号。
- **如有 UI 变更**：必须包含"使用 Chrome DevTools MCP 验证渲染"作为验收标准。

### 4. 功能需求
编号列表，使用"系统必须..."句式：
- "FR-1: 系统必须允许用户..."
- "FR-2: 当用户点击 X 时，系统必须..."

### 5. 非目标（范围外）
明确列出本次不做的事项，防止范围蔓延。

### 6. 技术考量（可选）
- 数据库变更说明
- API 契约变更
- 已知依赖或约束

### 7. 成功指标
如何衡量该功能是否成功。

### 8. 开放问题
需要进一步澄清的点。

---

## 项目规范约束（必须遵守）

生成的用户故事和验收标准必须隐含遵守以下项目规范（不需要在 PRD 中重复列出，但 Story 的实施必须符合）：

- **i18n 零容忍**：所有用户可见字符串必须通过 i18next 获取
- **Tailwind 语义变量**：使用 `bg-background`、`text-primary` 等语义化 class，禁止硬编码 HEX 颜色
- **600 行硬限制**：每个 Story 的实施结果不应导致任何业务文件超过 600 行
- **分层架构**：后端遵循 Controller → Service → Repository 三层架构
- **双主题兼容**：所有 UI 变更必须同时支持浅色/深色主题

---

## Story 拆分指导

### 合适大小的 Story：
- 新增一个数据库字段和迁移
- 在现有页面添加一个 UI 组件
- 更新一个 Service 方法的新逻辑
- 给列表页添加一个筛选下拉框

### 太大的 Story（必须拆分）：
- "构建整个仪表盘" → 拆为：schema、查询、UI 组件、筛选器
- "添加认证系统" → 拆为：schema、中间件、登录 UI、会话管理
- "重构 API" → 拆为：每个端点或模式一个 Story

### 排序规则：
1. Schema/数据库变更（迁移）
2. 后端逻辑（Service/Controller）
3. 前端 UI 组件
4. 聚合视图/集成测试

---

## 输出

- **格式：** Markdown (`.md`)
- **位置：** `tasks/` 目录（如不存在则创建）
- **文件名：** `prd-[feature-name].md`（kebab-case）

## 示例 PRD

```markdown
# PRD: 排位赛匹配系统

## 概览
为五子棋在线对弈添加排位赛模式，玩家通过 ELO 积分匹配实力相近的对手，提升竞技体验和用户留存。

## 目标
- 支持基于 ELO 积分的自动匹配
- 积分变化实时可见，增强成就感
- 匹配等待时间不超过 30 秒

## 用户故事

### ONLINE-030: 积分匹配后端逻辑
**描述:** 作为系统, 我想要基于 ELO 积分自动匹配实力相近的玩家, 以便提供公平的对局体验

**验收标准:**
- [ ] 匹配算法查找 ±200 ELO 范围内的等待玩家
- [ ] 无匹配时创建等待队列条目，设置 30 秒超时
- [ ] 匹配成功自动创建房间并通知双方
- [ ] TypeScript 编译通过
- [ ] 匹配逻辑单元测试通过

### ONLINE-031: 排位赛入口 UI
**描述:** 作为玩家, 我想要在大厅看到排位赛按钮并查看当前积分, 以便决定是否参与排位

**验收标准:**
- [ ] 大厅页面显示"排位赛"按钮（仅登录用户可见）
- [ ] 按钮旁显示当前 ELO 积分（rating > 0 时显示）
- [ ] 点击按钮触发匹配流程，按钮变为"匹配中..."状态
- [ ] TypeScript 编译通过
- [ ] 使用 Chrome DevTools MCP 验证渲染（浅色/深色主题）

## 功能需求
- FR-1: 系统必须支持基于 ELO 积分差值的匹配算法
- FR-2: 系统必须在匹配成功后自动创建排位房间
- FR-3: 排位赛结束后必须更新双方 ELO 积分

## 非目标
- 不包含自定义匹配规则（如地图选择、时间限制）
- 不包含排位赛赛季/排行榜功能
- 不包含观战排位赛功能

## 技术考量
- ELO 计算复用已有的 `eloService`
- 匹配队列使用 Redis sorted set（如已部署）或内存 Map
- 需要新增 `MatchMode` 枚举值 `RANKED`

## 成功指标
- 玩家在 30 秒内完成匹配率 > 80%
- 积分计算准确率 100%（与已有 ELO 测试用例一致）

## 开放问题
- 匹配超时后是否需要提示用户切换到普通模式？
- 是否需要积分变化动画效果？
```
